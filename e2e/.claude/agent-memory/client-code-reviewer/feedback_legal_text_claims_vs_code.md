Legal/policy copy (client/src/legal/*.md) tends to state user controls that do not exist or do something narrower. The 2026-09-26 review found: "Briefs can be turned off in Settings" (the toggle is device-local display-only; the server sweep still sends every open item to Anthropic), "trash stays recoverable until you empty it" (a /trash page exists but there is no empty-trash action and no server trash purge), "One person, one account" (the app deliberately supports multi-account), and the cookie name `better-auth.session_token` (it is `__Secure-`-prefixed in production because of useSecureCookies).

**Why:** Google OAuth verification and GDPR readers take these statements literally. A control the policy promises but the app lacks is a compliance defect, not a copy nit.

**How to apply:** For every sentence of the form "you can X", "X can be turned off", or "kept until Y", grep the client for the control and the api-server for the retention path. Round 2 found "revoke access by disconnecting the calendar": disconnect deletes the stored tokens but never calls Google revoke, so the grant stays listed in the Google Account. Round 3 (content revision) found scope contradictions rather than missing controls: a general sentence ("no one reads your notes, items or calendar data unless you opt in") followed by a stricter carve-out ("Google Calendar data is never included"), and the Limited Use paragraph listing fewer human-access exceptions (law, consent) than the general support/security bullet. Diff every exception list against its sibling. Round 4 found a purpose-limitation contradiction: the Limited Use paragraph said calendar data is "used only to provide the calendar-sync features" while the AI section discloses calendar event titles going to Anthropic, and the brief sweeper (LIVE_STATUSES includes `calendar`; GCal description syncs into notes) sends Google data to Anthropic automatically. Check every "used only for X" against every other section that names the same data. Round 5 found the logging blind spot: the policy scoped server logs to "route, timing, status, user id" while api-server `console.log`s Google event titles (calendar.ts, calendarPushback.ts) and email addresses (emailStub.ts) into Cloud Logging, which also breaks the Limited Use human-read exceptions; and `webhookDeliveries` keeps full entity payloads with no TTL or delete path. Grep `console.` for `title=`/`to=` and list every collection's TTL before approving retention text. Round 6: removing the interpolations + a static source-grep guard was NOT enough — `console.error(msg, err)` with a raw GaxiosError prints `config.data` (event summary + description) because gaxios's defaultErrorRedactor only strips auth/secret fields; verified with a local 403 stub. Static guards cannot see error objects; demand a redaction at the client (errorRedactor) plus a runtime test. Technical claims (AES-256-GCM, sha256 token hashes, what fields go to Anthropic) have been accurate so far. Also related: [[feedback-dom-predicate-faked-in-node-tests]]. renderToStaticMarkup is the node-env way to unit-test render props, and "no Testing Library" is not a reason to skip that.

Round 7 (public landing page, 2026-10-01): a NEW copy surface (`lib/landingContent.ts`, `-LandingPage.tsx`, index.html `<noscript>`) re-introduced both contradictions the privacy policy had already fixed ("AI features off until you turn them on"; "Calendar data used only for the features above" = sync only), and listed 3 of the 4 scopes the connect URL requests (the scope-pin test regex read only `REQUIRED_CALENDAR_SCOPES`, missing `USERINFO_EMAIL_SCOPE`). Fixes to policy text don't propagate to marketing/landing copy — diff every new public-copy surface against privacy-policy.md's AI and Limited Use sections, and pin scopes against the actual `scope: [...]` passed to generateAuthUrl.
