name: Reassign refactors silently expand GCal/webhook fan-out
description: When reassignEntity legs are refactored to flow through applyAndPublishOperation (or any path that runs notifyChange), the source-side delete leg picks up GCal pushback + webhook + per-item cascades that the previous recordOperation-only path did not have. Always check the cascade.
type: project
---

When reviewing changes that move `reassignEntity`'s persistence (in `api-server/src/lib/reassignEntity.ts`) onto a path that triggers `notifyChange` — `applyAndPublishOperation`, or any future shared apply pipeline — assume the source-side delete leg now does GCal/webhook fan-out it did NOT do under direct `recordOperation` calls.

Specific cascades that surface:
- Routine delete-leg → `hydrateRoutineDeleteSnapshots` populates the snapshot from the pre-delete row → `maybePushToGCal` → `pushRoutineDeletion` mass-trashes every calendar-status item generated by that routine on the source user AND deletes the source GCal master event. Pre-refactor neither happened.
- Calendar-linked item create-leg fires `pushExistingItemToGCal` against the just-created target event → redundant `provider.updateEvent` (idempotent today, wasteful and fragile).
- Webhook subscribers on the target user see `item.created` for the create leg (this one is intentional; flagged as the parity win in commit messages).

**Why:** Discovered during the api-overhaul-v1 reassign hardening review (2026-05). The diff comments highlighted webhook/SSE parity as a *win* but didn't mention the GCal cascade as a *side effect*; only the calendar-item double-push was even partially acknowledged. The destructive routine cascade was completely silent.

**How to apply:** On any reassign change that touches `persist*Move` helpers or substitutes `recordOperation` for `applyAndPublishOperation`, trace `notifyChange → maybePushToGCal` for both legs and ask "does this fan-out change behavior on the source user's GCal / generated items?" If yes and it's not explicitly a tested intent, flag as Critical and propose a `suppressGCalPushback` option on `ApplyOptions` (or a sentinel `deviceId` like `api:<tokenId>:reassign-source`) so reassign can opt out of GCal pushback while still recording the op + firing SSE/web push.
